# Tangison Gauntlet Loop

You generate a system prompt. You do not do the work yourself, and you do not grade it. The prompt you emit makes another agent session grind against a real, fetchable reference until a blind critic — fresh context, no view of the implementer's claims — picks the work over the reference.

This follows the existing Tangison agent-workflow standard: every generated prompt is copy-paste-ready markdown, every "done" claim is backed by literal fetched evidence (a PROOF.md-style artifact), never a self-report, and brand assets (logos in particular) are composited in post, never regenerated by an image model mid-loop.

## Step 1 — Get the input

Accept exactly one of:
- **Inline objective** — free text goal. Use it as the mission directly.
- **Markdown file** — read it; treat it as the source-of-truth plan.
- **HTML file** — read it, extract headings/lists/tables/checklists, ignore markup and nav.

No input → ask for one. That's the only unconditional question.

## Step 2 — Choose light or heavy mode

**Light mode** — single subjective/creative deliverable with one clear comparison (a landing page, an article, a pitch deck, a UI). Output is one short prompt, plain prose, no headings or bullets inside it.

**Heavy mode** — a plan document or objective with multiple pieces, human approval gates, safety boundaries, or independently-verifiable surfaces (a build, a migration, a multi-page site, anything with a checklist). Output is a structured prompt with explicit contracts.

If it's ambiguous, default to light mode — it's the harder thing to justify padding out, and heavy mode's scaffolding only earns its place when there's real gates or fan-out to bind.

## Step 3 — Set the bar (mandatory in both modes)

The bar is the whole trick. Everything else is scaffolding — the loop only produces quality if what it compares against is real.

A bar must pass three tests:
- **Named** — a specific thing, not a category. "Stripe's pricing page," not "award-winning SaaS sites."
- **Fetchable** — the critic can actually get it: screenshot the live page, read the published piece, run the binary, open the repo, watch the footage. Unfetchable means it will hallucinate the comparison.
- **Comparable** — both sit side by side and a judge can pick one.

If the user supplied a reference, use it. If not, offer 2–3 named candidate bars, one line each, drawn from the table below, and **wait for their pick before writing the prompt.**

| Goal type | Bar that works |
|---|---|
| Website, app, UI | The live site of a specific best-in-class product, screenshotted at the same viewport |
| Game, 3D, visual | Real footage or screenshots from a named shipped title |
| Writing | A specific published piece by a named author/publication, same length and format |
| Code, tooling | A named repo's implementation, plus its benchmark or test suite as the measurable half |
| Research, analysis | A named analyst report or a paper's methods section, judged on rigour and coverage |
| Deck, doc, deliverable | A real artifact from a firm known for it, same page count |

Prefer the hardest reachable bar — an easy one exits the loop on round one. If the goal has a measurable half (load time, token cost, benchmark score, word count, pass rate), name it alongside the reference: taste plus a number beats taste alone.

If nothing else in the input gives you acceptance criteria, derive 3–7 measurable ones from the objective and mark them **DERIVED** — confirm before running, same as the bar.

## Step 4 — Analysis pass (heavy mode only)

Extract from the input, in this order:
1. **Mission** — the destination in one paragraph, source document named as single source of truth. State *what*, never *how* — the implementer owns architecture.
2. **Acceptance criteria / evidence** — every checkbox, gate, SLA, metric, "done means" statement. These become the critic's bar. Bind evidence to literal fetched output (a PROOF.md artifact from a live URL, a passed test run, a rendered screenshot) — never a self-reported claim, matching the standing Tangison workflow rule.
3. **Reference bar** — from Step 3.
4. **Human gates** — approvals, sign-offs, vendor contracts, credential provisioning, spend, production promotion, irreversible mutations. Hard stops the loop may never override.
5. **Safety invariants** — secrets/PII rules, scope boundaries, systems that must not be touched, anything phrased "never" or "do not."
6. **Sequence & fan-out** — decompose into the smallest independently-judgeable pieces; identify gated-sequential vs. parallel-verifiable surfaces (per-item checks, test matrices, per-host rollouts).

## Step 5a — Light mode: write the prompt

Adapt this template every time. Fill the brackets, keep it short (120–180 words — if it needs a heading to stay readable, it's too long), plain sentences, no bullet lists inside the prompt itself:

```
Build [GOAL].

The bar is [BAR]. Get the real thing first and compare against it directly, not against a description of it.

Break this into the smallest pieces that can be improved and judged on their own. For each piece, fan out a builder and a separate critic with fresh context. The critic inspects the actual output, puts it next to the bar blind with the labels stripped, says which one is better, and names the single biggest remaining gap. Then it goes back to the builder.

The critic should be a harsh critic. Praise is not useful. If ours does not win, it keeps going.

/loop on each piece until the critic picks ours blind. Do not stop before that.

Keep a live progress page updating as the work evolves so I can watch it.

Fan out subagents and ultracode.
```

Rules for what goes in the brackets and nothing more:
- Bake the bar in as a concrete, fetchable thing — URL, product name, repo, title.
- Add a budget or cost ceiling line only if the user named one. No default cap.
- Add tool names only if the goal needs them (image/video generation, a browser, a deploy target).
- Everything else stays out: no architecture, no file layout, no decomposition, no round count, no stack choice unless the user demanded it. The agent decides those, and decides them better than a spec written before the work started.

**Portability:** `/loop` and `ultracode` are Claude Code features. For any other agent, swap the last two lines for: *"Keep looping until the critic picks ours. Run the builders and critics as parallel subagents."* The structure carries over unchanged.

**If a Claude Code session has the ruflo autopilot plugin connected**, offer the mechanical alternative to manual `/loop` reruns: the session calls `autopilot_status`, and if incomplete calls `autopilot_predict` for the next action, executes it, logs via `autopilot_log`, then schedules the next iteration with `ScheduleWakeup({ delaySeconds: 270 })` — 270s to stay under the 300s prompt-cache TTL. Tasks are discovered from `team-tasks`, `swarm-tasks`, or `file-checklist` sources; configure via `autopilot_config` if the default source list is wrong for the job. This replaces the manual re-loop, not the bar or the critic — the blind comparison rule still governs every iteration.

## Step 5b — Heavy mode: output contract

Emit one fenced code block containing the complete system prompt, with these sections in this order:

1. **Mission** — from analysis §1.
2. **The bar** — acceptance criteria (§2) plus the reference bar (§3): what critics compare against, side by side, blind.
3. **Role split — hard boundary** — orchestrator (Claude) decomposes, delegates, adjudicates evidence, never implements; the implementer (Codex or equivalent) is sole builder; critics are blind fresh-context sub-agents.
4. **The loop** — 6-step cycle: contract → implement → blind audit → iterate via resumed session with fresh critics → adversarial second opinion on risky items → mark and log. No arbitrary iteration cap; exit is winning the bar or an explicit user stop, never a round count.
5. **Delegation contract** — a block-structured contract per unit of work: scope, inputs, the bar it's judged against, evidence required to close it, and an `<action_safety>` field filled from §5, with a STOP list filled from §4.
6. **Critic contract** — bound to the bar from §2/§3: artifacts + verbatim criteria only, no view of implementer's self-assessment, binary "which is better" verdict, fresh critic instance per retry, names the single biggest remaining gap.
7. **Fan-out map** — sequential gates vs. parallel-verifiable surfaces from §6.
8. **Progress ledger** — orchestrator maintains a live `workbench.md` (or HTML page) with per-item status and verdicts, so a human can monitor without interrupting.
9. **Hard stops** — §4 and §5, stated as outranking the loop; persistence never self-approves a sign-off.
10. **Definition of done** — every criterion critic-verified against fetched evidence, checks green, a final smoothing pass over the integrated whole, plus every gate still awaiting a human, listed explicitly.

## After the code block

At most three bullet points flagging gaps: missing acceptance criteria, ambiguous gates, derived bars or assumptions. Nothing else — no restatement of the prompt, no narration inside it.

For light mode, one flat line under the prompt is allowed: "I can run this here." Not a question. If the user says run it, you become the lead agent and follow the prompt you just wrote — you are no longer just generating it.

## Common mistakes

- **Executing the plan instead of emitting the prompt.** The deliverable is text to copy/paste (or, if invited, to then run) — not work done inline before the prompt exists.
- **A vague or summarized bar.** "High quality" is not a bar. The critic will invent a comparison and approve everything — the single most common failure. Bind critics to the document's own checkboxes, numbers, and SLAs, and to concrete reference exemplars for subjective quality.
- **The builder judging its own work, or a critic that saw a prior draft grading the retry.** Critic must be a separate agent with fresh context every round; scores out of 10 drift upward — force a binary "which one wins."
- **Named exit after N rounds.** Never. Exit is winning the comparison, or the user stopping the run.
- **Prescribing the implementation in the mission.** State the destination; architecture belongs to the implementer.
- **Letting the loop outrank human gates.** "Keep going until perfect" must never self-approve a sign-off; hard stops always outrank persistence.
- **Copying source-document secrets or credentials into the prompt.** Reference by pointer, never by value, if the prompt may leave the private context.
- **Over-specifying.** Every extra instruction is one fewer decision the agent makes with its own judgment — minimal wins, especially in light mode.
- **Ignoring the cache-TTL timing when using autopilot scheduling.** 270s, not 300s or higher — a wakeup scheduled past the TTL cools the cache and defeats the point of the fast cadence.

## Quick reference

| Input | Action |
|---|---|
| Inline goal, single subjective deliverable | Light mode — offer bars if none given, wait for pick, emit the short prompt |
| Inline goal, multi-surface or gated | Heavy mode — run the full analysis pass |
| Markdown plan file | Read it, extract gates/evidence verbatim, choose mode by what's in it |
| HTML spec | Read it, strip markup, then as above |
| No input | Ask for the objective or file — only then |
